## What counts as a GitHub Achievement?

GitHub's **activity achievements** are profile decorations associated with activity such as merged pull requests, accepted discussion answers, or stars received by a repository. They are different from account or program badges such as **Pro** or **GitHub Campus Expert**.

The profile reference currently describes program badges, but it does not give award rules or tier cutoffs for the activity achievements in this guide. Accordingly:

- **Verified artwork** means the image URL below returned an image from `github.com/images/modules/profile/achievements/` when checked.
- **Verified process** means GitHub Docs explain the underlying GitHub feature, such as creating a pull request or marking a discussion answer as accepted. It does **not** mean those docs guarantee an achievement award.
- **Tier cutoffs** are marked *not published in the official documentation reviewed* unless a GitHub source explicitly provides a value.
- **Availability** is marked *uncertain* when GitHub's public docs do not confirm whether a badge can still be earned.

For your own status, open your GitHub profile and inspect its Achievements section. This repository does not know whether any reader has earned a badge, and GitHub may delay, change, or omit awards.

## Achievement-by-achievement guide

The activity descriptions below are cautious summaries of the achievement names and commonly displayed badge descriptions. GitHub's public documentation reviewed for this guide does not make the activity-to-award rules or numeric thresholds contractual. Follow the legitimate workflow, then confirm the result on your profile rather than treating any step here as a guarantee.

### Pull Shark

**Recognizes:** Pull-request contribution activity; the badge is associated with merged pull requests.

**Eligibility and tiers:** A merged pull request is the relevant activity. GitHub's public documentation does not specify the exact number or type of merges required, tier cutoffs, or whether all repositories and merge methods qualify. Tier variants exist in GitHub-hosted artwork, but their thresholds are not documented in the official references reviewed.

**Availability:** The image is live on GitHub's host. Public docs reviewed do not confirm current award availability or exact eligibility.

**A legitimate way to work toward it**

1. Find a maintained project that you genuinely use or understand.
2. Read its contribution guide, open issues, and project conventions.
3. Select a useful, appropriately scoped fix or improvement.
4. Create a branch, make and test the change, then open a clear pull request.
5. Respond constructively to feedback and update the change as needed.
6. If the maintainers accept the work, let them merge it; check your profile later.

**Example:** Fix a reproducible keyboard-navigation bug in a library you use, add a regression test, and submit the change with steps to reproduce and test results.

**Prerequisites and limits:** The project decides whether to review and merge a contribution. Opening a pull request alone is not the same as having it merged. No official numeric tier thresholds were found.

**Official process:** [Creating a pull request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request) · [Pull request reviews](https://docs.github.com/en/pull-requests/reference/pull-request-reviews)

### YOLO

**Recognizes:** A pull request merged without a review, according to the commonly displayed badge description.

**Eligibility and tiers:** The no-review condition is not spelled out in the official GitHub documentation reviewed as an achievement rule. GitHub does not publicly specify additional requirements or tier cutoffs here. Do not deliberately avoid review to chase this badge.

**Availability:** The GitHub-hosted image is live; current award availability is not confirmed in public docs.

**A legitimate way to work toward it**

1. Contribute a small, low-risk change to a repository where you have permission to merge.
2. Follow the repository's required checks and branch-protection rules.
3. Use sound judgment: request review whenever policy, risk, or project practice calls for it.
4. Only merge when the work is ready and you are authorized to do so.
5. Check your profile; never bypass safeguards just to try to trigger an achievement.

**Example:** A maintainer fixes a typo in a README in their own small project and merges it under that project's normal process, which does not require a second reviewer.

**Prerequisites and limits:** You need an authorized path to merge a pull request. Repository settings or organizational policy may require review. There is no supported tier progression published in the sources reviewed.

**Official process:** [About pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests) · [About protected branches and required reviews](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-pull-request-reviews-before-merging)

### Galaxy Brain

**Recognizes:** Helpful answers in GitHub Discussions that are marked as accepted.

**Eligibility and tiers:** The relevant workflow is an answer marked as accepted in a Discussion's question-and-answer category. GitHub Docs describe accepted answers as a Discussions feature, but do not specify achievement thresholds or guarantee an award for any particular answer.

**Availability:** The GitHub-hosted image is live; public docs reviewed do not confirm current award availability or tiers.

**A legitimate way to work toward it**

1. Join a project with Discussions enabled and a question-and-answer category.
2. Read the question and earlier replies before responding.
3. Give a specific, accurate answer; include a minimal example or a reliable reference when useful.
4. Be open to correction and clarify your answer if the conversation develops.
5. The discussion author or a maintainer can mark a helpful answer as accepted.
6. Check your profile after participating; acceptance does not guarantee an achievement.

**Example:** Explain why a particular API call returns a permission error, show the corrected permission scope, and link to the relevant documentation. The question author marks the answer as accepted.

**Prerequisites and limits:** Discussions must be enabled, and the category must support accepted answers. Another participant's decision is involved; do not post repetitive or low-value answers to solicit acceptance.

**Official process:** [About GitHub Discussions](https://docs.github.com/en/discussions/collaborating-with-your-community-using-discussions/about-discussions) · [Participating in a discussion](https://docs.github.com/en/discussions/collaborating-with-your-community-using-discussions/participating-in-a-discussion)

### Quickdraw

**Recognizes:** Historically, this badge has been associated with resolving an issue or pull request very quickly (often described as within five minutes). That time rule is **not confirmed by the official GitHub documentation reviewed here**.

**Eligibility and tiers:** Exact requirements and tier rules are not publicly verified in the cited official docs. Do not rely on a short timer as an official rule.

**Availability:** **Uncertain.** A live GitHub image URL proves that artwork is served; it does not prove the achievement can still be earned. No official current availability statement was found.

**A responsible approach**

1. Do not create or close issues or pull requests just to race a clock.
2. If a real issue is already resolved, document the solution and close it according to the project's process.
3. If a pull request is no longer needed, explain why and close it respectfully.
4. Check GitHub's current profile UI and official announcements for availability; treat the badge as historical unless GitHub confirms otherwise.

**Example:** A maintainer closes a duplicate report after linking the canonical issue and explaining where the discussion will continue. The action is taken for project clarity, not to trigger a badge.

**Prerequisites and limits:** Issue and pull-request permissions and project conventions apply. The often repeated timing rule and current earnability are unverified, so no earning result or timeframe can be promised.

**Official process:** [About issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/learning-about-issues/about-issues) · [Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests)

### Pair Extraordinaire

**Recognizes:** Pairing or co-authoring contributions associated with merged pull requests, according to the commonly displayed badge description.

**Eligibility and tiers:** GitHub's public docs reviewed do not state the achievement's exact co-authoring rules, required number of collaborations, or tier cutoffs. Merely adding another person's name without their real contribution is not legitimate co-authoring.

**Availability:** The image is live on GitHub's host; exact current eligibility and tiers are not confirmed in public docs.

**A legitimate way to work toward it**

1. Find a real task that benefits from two contributors working together.
2. Agree on the task and divide or jointly perform the work transparently.
3. Credit each contributor accurately using the repository's contribution conventions.
4. Test the result and open a pull request that explains the collaboration.
5. Work with maintainers through review; if accepted, let the pull request be merged.
6. Confirm any award on your profile rather than assuming co-authorship triggered it.

**Example:** Two contributors debug a race condition together, pair on the fix and tests, then submit one pull request with accurate co-author credit.

**Prerequisites and limits:** Genuine collaboration and a merged pull request are central to the commonly displayed description. The other contributor and maintainers are involved; do not fabricate co-authorship.

**Official process:** [Creating a pull request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request) · [About commit authorship](https://docs.github.com/en/pull-requests/how-tos/commit-changes/creating-a-commit-with-multiple-authors)

### Starstruck

**Recognizes:** A repository's popularity, represented by stars, commonly described in relation to a repository you created.

**Eligibility and tiers:** The exact ownership, counting, and award thresholds are not specified in the official docs reviewed. GitHub-hosted artwork has tier variants, but this guide does not assign numbers to them because no official cutoff table was found.

**Availability:** The image is live; award availability and thresholds are not confirmed in public docs.

**A legitimate way to work toward it**

1. Build a useful project that solves a real problem or teaches something clearly.
2. Write a concise README with setup steps, examples, and limitations.
3. Maintain the project: triage issues, review contributions, and publish meaningful releases.
4. Share it in communities where it is relevant, following their rules and avoiding unsolicited promotion.
5. Treat stars as a signal of interest, not a target to manipulate.
6. Check your profile for any achievement and its displayed tier.

**Example:** Publish a small, well-documented accessibility testing tool, respond to user reports, and accept thoughtful improvements from the community.

**Prerequisites and limits:** Stars come from other users choosing to save a repository. GitHub Docs describe what starring does, but do not guarantee a badge or publish its thresholds.

**Official process:** [Saving repositories with stars](https://docs.github.com/en/get-started/exploring-projects-on-github/saving-repositories-with-stars) · [Quickstart for repositories](https://docs.github.com/en/repositories/creating-and-managing-repositories/quickstart-for-repositories)

### Historical and limited badges

#### Arctic Code Vault Contributor

**What it refers to:** GitHub's Archive Program documents a snapshot of active public repositories captured on **February 2, 2020** for preservation in the Arctic Code Vault.

**Eligibility and availability:** The archive event was a one-time snapshot, not an ongoing contribution program. GitHub's public Archive Program page confirms the snapshot, but does not specify a badge-award cutoff or complete eligibility rules. There is no documented current action plan to earn this badge; do not claim that a new contribution can qualify.

**Historical context steps**

1. Read the [GitHub Archive Program](https://archiveprogram.github.com/) and [Arctic Code Vault](https://archiveprogram.github.com/arctic-vault/) background.
2. If the badge is already displayed on your profile, treat the profile as the source for your personal award status.
3. Do not make new contributions expecting to receive this historical badge.

**Example:** The Archive Program page says GitHub captured an active-public-repository snapshot on February 2, 2020; that historical event does not establish a present-day earning route.

**Tiers:** No active tier progression is documented in the official sources reviewed.

#### Mars 2020 Contributor

**What it refers to:** A legacy badge artwork associated with the Mars 2020 period.

**Eligibility and availability:** The original badge image is still served by GitHub, but the official references reviewed do not establish its award criteria, cutoff, or whether it can still be earned. Treat it as **historical / availability unverified**, not as an active goal.

**Historical context steps**

1. Check GitHub's own current profile display and any official announcement you can find for the award.
2. If already shown on your profile, use that as evidence of your own award.
3. Do not create activity or claim eligibility based only on the surviving image URL.

**Example:** Seeing the badge artwork in this gallery confirms only that GitHub's image server still has the file; it does not confirm the underlying event or a new earning route.

**Tiers:** No verified tier progression or active eligibility was found in the official sources reviewed.

## A legitimate roadmap

The time ranges below are **planning estimates only**, not GitHub requirements, guarantees, or expected award dates. Some outcomes depend on maintainers, reviewers, discussion authors, and other users.

### Beginner level

**Estimated timeframe:** 1-3 weeks to learn the workflow; continued practice thereafter.

**Action plan**

1. Complete GitHub's [repository quickstart](https://docs.github.com/en/repositories/creating-and-managing-repositories/quickstart-for-repositories).
2. Learn the difference between repositories, branches, commits, issues, pull requests, discussions, and stars.
3. Personalize your profile honestly and pin projects that represent your work.
4. Read contribution guides before opening issues or pull requests.
5. Star projects you genuinely want to revisit; a star is a bookmark and a show of interest, not an achievement guarantee.
6. Pick one small documentation or bug-fix contribution and follow it through review.

**Realistic introductory milestones**

- Open a useful issue with reproduction steps.
- Make a first meaningful contribution to a project.
- Understand that a pull request must be merged for the commonly described Pull Shark activity.
- Understand that stars received by a project depend on other users.
- Do not expect a badge for merely creating an account, starring repositories, or opening a pull request.

**Progress checklist**

- [ ] I can create a repository and make a commit.
- [ ] I can explain the purpose of an issue and a pull request.
- [ ] I have read a project's contribution guidelines before contributing.
- [ ] I have opened or reviewed a real pull request.
- [ ] I understand that badge thresholds and availability are not fully documented.

### Intermediate level

**Estimated timeframe:** 1-3 months of regular, sustainable contribution; highly dependent on projects and review cycles.

**Action plan**

1. Choose a project whose code, documentation, or community you can support over time.
2. Start with issues marked for contributors, but confirm they are still relevant.
3. Propose a focused change with tests or clear before-and-after evidence.
4. Ask for review when appropriate and respond to feedback without defensiveness.
5. Participate in Discussions only when you have a useful question, answer, or project insight.
6. For questions, explain your reasoning and cite dependable sources; accepted answers are chosen by the question author or maintainers.
7. Try genuine pairing on a task only when collaboration would improve the work.

**Achievement connections**

- Pull Shark: merged pull requests are the commonly described activity; exact thresholds are not published in docs.
- Galaxy Brain: useful answers may be marked accepted in Discussions; another participant is involved.
- Pair Extraordinaire: the commonly displayed description involves co-authored merged work; collaborate and credit truthfully.
- YOLO: never bypass a required review for an award; follow project policy.

**Progress checklist**

- [ ] I have submitted a focused contribution that solves a real problem.
- [ ] I have reviewed another contributor's work or learned from a maintainer's review.
- [ ] I have contributed a substantive answer or discussion where I could help.
- [ ] I understand how accepted answers work and who can mark one.
- [ ] I have paired with someone on real work and used accurate credit, if relevant.

### Advanced level

**Estimated timeframe:** Several months or longer. Community recognition and higher profile tiers cannot be scheduled or guaranteed.

**Action plan**

1. Build a consistent, sustainable history of useful contributions across projects you care about.
2. Take ownership of maintenance tasks: improve tests, clarify docs, triage issues, or mentor new contributors.
3. Help projects reduce friction with clear contribution guides, reproducible bug reports, and respectful reviews.
4. When maintaining a repository, enable and moderate Discussions thoughtfully; mark answers only when they genuinely resolve the question.
5. Grow a project through quality, reliability, and relevant community engagement—not star requests, spam, or artificial activity.
6. Keep security and branch-protection safeguards in place; achievement chasing is never a reason to weaken them.
7. Review your profile periodically. GitHub may award, tier, hide, or change achievements independently of this guide.

**Higher-tier and dependent outcomes**

- Some activity badges have tiered variants, but the official documentation reviewed does not publish reliable numeric cutoffs.
- Starstruck depends on stars from other users; audience response is outside the maintainer's control.
- Galaxy Brain depends on an answer being accepted by the discussion author or an authorized maintainer.
- Pair Extraordinaire depends on genuine collaboration and how GitHub recognizes co-authored work.
- Quickdraw's current availability and commonly repeated timing description are unverified; do not build a plan around it.
- Arctic Code Vault Contributor relates to a 2020 snapshot; Mars 2020 Contributor is historical/uncertain. Neither has a verified current earning path here.

**Progress checklist**

- [ ] I have contributed over time without manufacturing activity.
- [ ] I have helped another person understand or improve a project.
- [ ] I have maintained quality and security standards even when they add review steps.
- [ ] I accept that tiers and community-dependent outcomes are not guaranteed.
- [ ] I checked my profile directly instead of assuming an achievement was awarded.
