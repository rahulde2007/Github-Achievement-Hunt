## ✦ At a glance

GitHub **activity achievements** are profile decorations associated with activity such as merged pull requests, accepted Discussion answers, or stars received by a repository. They are distinct from program or account badges such as **Pro** and **GitHub Campus Expert**.

| Label | What it means here |
| --- | --- |
| `VERIFIED ARTWORK` | GitHub-hosted image endpoint returned image content when checked. |
| `ACTIVITY GUIDE` | GitHub Docs explain the underlying feature; they do not guarantee an achievement award. |
| `AVAILABILITY UNCERTAIN` | Current award eligibility is not confirmed in GitHub's public docs reviewed. |
| `HISTORICAL` | Associated with a past event; no current earning route is documented here. |

> [!NOTE]
> **Check your own profile** to confirm awards and displayed tiers. This guide does not claim that the repository owner or any reader has earned an achievement. GitHub may delay, change, or omit awards.

## 🎯 How to Earn Each Achievement

> [!TIP]
> Each guide separates the **commonly associated activity** from the **officially documented process**. Where GitHub has not published award rules or thresholds, none are inferred. Make useful contributions first; check the profile afterward.

### Pull Shark

<div align="center">
<img src="https://github.com/images/modules/profile/achievements/pull-shark-default.png" width="112" alt="Original GitHub Pull Shark achievement badge" />
</div>

**Recognizes:** Pull-request contribution activity, commonly associated with merged pull requests.

**Eligibility & tiers:** A merged pull request is the commonly described activity. GitHub's public docs reviewed do not specify how many merges are required, which merge methods qualify, or official tier cutoffs. Tier variants exist in GitHub-hosted artwork, but their thresholds are not documented in the sources reviewed.

**Availability:** `AVAILABILITY UNCERTAIN` — image is live; current award eligibility is not confirmed by the public docs reviewed.

**A legitimate path**

1. Find a maintained project you genuinely use or understand.
2. Read its contribution guide, issues, and conventions.
3. Choose a useful, appropriately scoped fix or improvement.
4. Create a branch, make and test the change, then open a clear pull request.
5. Respond constructively to feedback and revise as needed.
6. If maintainers accept it, let them merge the work; check your profile later.

**Example:** Fix a reproducible keyboard-navigation bug in a library you use, add a regression test, and submit the change with reproduction steps and test results.

**Limits:** Opening a pull request is not the same as having it merged. Project maintainers decide whether to accept the work. No official numeric tier thresholds were found.

**Official process:** [Creating a pull request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request) · [Pull request reviews](https://docs.github.com/en/pull-requests/reference/pull-request-reviews)

### YOLO

<div align="center">
<img src="https://github.com/images/modules/profile/achievements/yolo-default.png" width="112" alt="Original GitHub YOLO achievement badge" />
</div>

**Recognizes:** Commonly associated with a pull request merged without a review.

**Eligibility & tiers:** The no-review description is not specified in GitHub Docs as an achievement-award rule. GitHub does not publish additional requirements or tier cutoffs in the sources reviewed.

**Availability:** `AVAILABILITY UNCERTAIN` — image is live; current award eligibility is not confirmed.

**A responsible path**

1. Work on a small, low-risk change in a repository where you have permission to merge.
2. Follow required checks, branch-protection rules, and project policies.
3. Request review whenever project practice, policy, or risk calls for it.
4. Merge only when the change is ready and you are authorized to do so.
5. Check your profile; never bypass safeguards to pursue an achievement.

**Example:** A maintainer fixes a typo in their own small project and merges it through that project's ordinary process, which does not require another reviewer.

**Limits:** You need an authorized path to merge. Organizational policy or repository settings may require review. There is no verified tier progression in the sources reviewed.

**Official process:** [About pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests) · [Protected branches and required reviews](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-pull-request-reviews-before-merging)

### Galaxy Brain

<div align="center">
<img src="https://github.com/images/modules/profile/achievements/galaxy-brain-default.png" width="112" alt="Original GitHub Galaxy Brain achievement badge" />
</div>

**Recognizes:** Helpful answers in GitHub Discussions that are marked as accepted.

**Eligibility & tiers:** GitHub Docs describe accepted answers as a Discussions feature, but do not specify achievement thresholds or guarantee an award for any answer.

**Availability:** `AVAILABILITY UNCERTAIN` — image is live; current award eligibility and tier cutoffs are not confirmed in public docs.

**A legitimate path**

1. Join a project with Discussions enabled and a question-and-answer category.
2. Read the question and earlier replies before responding.
3. Give a specific, accurate answer; add a minimal example or reliable reference when useful.
4. Be open to correction and clarify your answer if needed.
5. The discussion author or a maintainer can mark a helpful answer as accepted.
6. Check your profile after participating; acceptance is not an award guarantee.

**Example:** Explain why an API call returns a permission error, show the corrected permission scope, and link to the relevant docs. The question author marks the answer accepted.

**Limits:** Discussions must be enabled, and the category must support accepted answers. Another participant is involved; do not post repetitive or low-value answers to solicit acceptance.

**Official process:** [About GitHub Discussions](https://docs.github.com/en/discussions/collaborating-with-your-community-using-discussions/about-discussions) · [Participating in a discussion](https://docs.github.com/en/discussions/collaborating-with-your-community-using-discussions/participating-in-a-discussion)

### Quickdraw

<div align="center">
<img src="https://github.com/images/modules/profile/achievements/quickdraw-default.png" width="112" alt="Original GitHub Quickdraw achievement badge" />
</div>

**Recognizes:** Historically associated with resolving an issue or pull request very quickly, often described as within five minutes. This timing rule is **not confirmed** in the GitHub Docs reviewed.

**Eligibility & tiers:** Exact requirements and tier rules are not publicly verified in the cited official docs. Do not rely on a short timer as an official rule.

**Availability:** `AVAILABILITY UNCERTAIN` — a live image URL does not prove the achievement can still be earned. No official current availability statement was found.

**A responsible approach**

1. Do not create or close issues or pull requests to race a clock.
2. If a real issue is resolved, document the solution and close it according to project process.
3. If a pull request is no longer needed, explain why and close it respectfully.
4. Check GitHub's current profile UI and official announcements; treat it as historical unless GitHub confirms otherwise.

**Example:** A maintainer closes a duplicate report after linking the canonical issue and explaining where the discussion continues. The action is for project clarity, not a badge.

**Limits:** Permissions and project conventions apply. The commonly repeated timing rule and current earnability remain unverified; no result or timeframe can be promised.

**Official process:** [About issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/learning-about-issues/about-issues) · [Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests)

### Pair Extraordinaire

<div align="center">
<img src="https://github.com/images/modules/profile/achievements/pair-extraordinaire-default.png" width="112" alt="Original GitHub Pair Extraordinaire achievement badge" />
</div>

**Recognizes:** Pairing or co-authoring contributions associated with merged pull requests, according to the commonly displayed description.

**Eligibility & tiers:** GitHub's public docs reviewed do not state exact co-authoring rules, required collaborations, or tier cutoffs. Adding a person's name without their real contribution is not legitimate co-authoring.

**Availability:** `AVAILABILITY UNCERTAIN` — image is live; current eligibility and tiers are not confirmed in public docs.

**A legitimate path**

1. Find a real task that benefits from two contributors working together.
2. Agree on the task and divide or jointly perform the work transparently.
3. Credit contributors accurately and follow repository conventions.
4. Test the result and open a pull request that explains the collaboration.
5. Work with maintainers through review; if accepted, let the pull request be merged.
6. Confirm any award on your profile rather than assuming co-authorship triggered it.

**Example:** Two contributors debug a race condition together, pair on the fix and tests, then submit one pull request with accurate co-author credit.

**Limits:** Genuine collaboration and merged work are central to the commonly displayed description. The co-author and maintainers are involved; never fabricate credit.

**Official process:** [Creating a pull request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request) · [Creating a commit with multiple authors](https://docs.github.com/en/pull-requests/how-tos/commit-changes/creating-a-commit-with-multiple-authors)

<div align="center">
<img src="https://github.com/images/modules/profile/achievements/starstruck-default.png" width="112" alt="Original GitHub Starstruck achievement badge" />
</div>

**Recognizes:** A repository's popularity, represented by stars, commonly described in relation to a repository you created.

**Eligibility & tiers:** Exact ownership, counting, and award thresholds are not specified in the official docs reviewed. Tier variants exist in GitHub-hosted artwork, but no official cutoff table was found.

**Availability:** `AVAILABILITY UNCERTAIN` — image is live; award availability and thresholds are not confirmed in public docs.

**A legitimate path**

1. Build a useful project that solves a real problem or teaches something clearly.
2. Write a concise README with setup steps, examples, and limitations.
3. Maintain the project: triage issues, review contributions, and publish meaningful releases.
4. Share it where relevant, follow community rules, and avoid unsolicited promotion.
5. Treat stars as a signal of interest, not a target to manipulate.
6. Check your profile for any achievement and its displayed tier.

**Example:** Publish a well-documented accessibility testing tool, respond to user reports, and accept thoughtful improvements.

**Limits:** Stars come from other users choosing to save a repository. GitHub Docs explain starring but do not guarantee a badge or publish thresholds.

### 🌱 Beginner level

**Explanation:** Learn the building blocks and contribute carefully before worrying about badges.

**Action plan**

1. Complete GitHub's [repository quickstart](https://docs.github.com/en/repositories/creating-and-managing-repositories/quickstart-for-repositories).
2. Learn repositories, branches, commits, issues, pull requests, Discussions, and stars.
3. Personalize your profile honestly and pin projects that represent your work.
4. Read contribution guides before opening issues or pull requests.
5. Star projects you genuinely want to revisit; starring is not an achievement guarantee.
6. Choose one small documentation or bug-fix contribution and follow it through review.

**Achievement connections:** Learn that Pull Shark is commonly associated with merged pull requests, that repository stars depend on other users, and that account setup or opening a PR alone does not imply an achievement.

**Progress checklist**

- [ ] I can create a repository and make a commit.
- [ ] I can explain the purpose of an issue and a pull request.
- [ ] I read a project's contribution guidelines before contributing.
- [ ] I opened or reviewed a real pull request.
- [ ] I understand badge thresholds and availability are not fully documented.

### 🛠️ Intermediate level

**Explanation:** Build a track record of useful contributions and constructive collaboration.

**Action plan**

1. Choose a project whose code, documentation, or community you can support.
2. Find a relevant issue and confirm it is still open and useful.
3. Propose a focused change with tests or before-and-after evidence.
4. Ask for review when appropriate and respond to feedback constructively.
5. Join Discussions only when you have a useful question, answer, or project insight.
6. Explain your reasoning in answers and cite dependable sources; accepted answers are chosen by the question author or maintainers.
7. Pair on real work when collaboration improves the outcome.

**Achievement connections**

- **Pull Shark:** Merged PRs are the commonly described activity; thresholds are not published.
- **Galaxy Brain:** Accepted Discussion answers involve another participant's decision.
- **Pair Extraordinaire:** Commonly associated with genuine co-authored merged work; give accurate credit.
- **YOLO:** Never bypass a required review to pursue an award.

**Progress checklist**

- [ ] I submitted a focused contribution that solves a real problem.
- [ ] I reviewed another contributor's work or learned from maintainer feedback.
- [ ] I contributed a substantive answer or discussion where I could help.
- [ ] I know who can mark an answer accepted.
- [ ] I collaborated on real work and used accurate credit, if relevant.

### 🚀 Advanced level

**Explanation:** Sustain community value and understand which outcomes depend on other people.

**Action plan**

1. Build a consistent, sustainable history of useful contributions across projects you care about.
2. Take on maintenance tasks: improve tests, clarify docs, triage issues, or mentor contributors.
3. Make participation easier with clear guides, reproducible reports, and respectful reviews.
4. If you maintain a project, enable and moderate Discussions thoughtfully; mark answers only when they resolve the question.
5. Grow a project through quality and relevant community engagement—not star requests, spam, or artificial activity.
6. Keep security and branch-protection safeguards in place.
7. Review your profile periodically; GitHub may award, tier, hide, or change achievements independently of this guide.

**Achievement connections & dependencies**

- Some activity badges have tiered variants, but official numeric cutoffs are not published in sources reviewed.
- **Starstruck** depends on stars from other users; audience response is outside your control.
- **Galaxy Brain** depends on another participant accepting an answer.
- **Pair Extraordinaire** depends on genuine collaboration and how GitHub recognizes co-authored work.
- **Quickdraw**'s current availability and commonly repeated timing description are unverified.
- **Arctic Code Vault Contributor** relates to a 2020 snapshot; **Mars 2020 Contributor** is historical/uncertain. No current earning route is verified here.

**Progress checklist**

- [ ] I contributed over time without manufacturing activity.
- [ ] I helped another person understand or improve a project.
- [ ] I maintained quality and security standards, including required review.
- [ ] I accept that tiers and community-dependent outcomes are not guaranteed.
- [ ] I checked my profile instead of assuming an achievement was awarded.
